# Search Probes form-filter audit

This is a source audit of the advertised form in `mods/search-probes`, compared with
`resident_search_protocol.py`, `system_query_snapshot.py`, and the resident evaluator. “Advertised”
means a field rendered by `resident_search_overlay.py`; criteria accepted by the protocol but not
rendered are called out separately. `Any` is sparse: it omits the criterion rather than matching a
sentinel value.

## Evaluation model

The native scan event performs the cheap system predicate. The resident then evaluates the copied
generated snapshot. Generated planet, weather, palette, metadata, and spawn data are captured only
when a corresponding criterion needs them. Object-backed floating-island criteria trigger a second
capture with resolved object lists, after cheaper predicates. A criterion not in `SNAPSHOT_CRITERIA`
is evaluated through the native candidate path after the snapshot passes.

All planet criteria in one request are a conjunction on one planet. “Contains …” system criteria are
independent aggregates and can be satisfied by different planets. The first matching planet is the
navigation target.

## Findings and remaining cleanup

1. The two floating-island controls are not duplicates. Terrain is a cheap exact generated terrain
   family; object-backed islands are a resolved spawn/object-list fact. HydroGarden is a biome
   subtype and is neither control. Retained survey evidence found HydroGarden records but only a
   subset had floating-island object flags, so collapsing these controls would create false results.
2. “Water”, “Deep water”, “Waterworld”, “Extreme storms”, “Sentinels”, and the corresponding
   “Contains …” rows are separate fields and scopes. Keep them, but group target-planet and
   system-aggregate controls visually and avoid repeated unqualified labels.
3. The implementation de-duplicates resource selections and requires every selected ID on the same
   planet. The current UI presents the slots as “Required resource (all)” and empty slots are
   ignored. The protocol also accepts singular `resource` for programmatic callers, but no form
   widget advertises it; keep it as a compatibility/API criterion or remove it deliberately, not as
   a second UI concept.
4. `anomaly` is genuinely distinct and native-only. It must remain in the system tab, but its
   generated-snapshot absence should be explicit in diagnostics and tests.
5. “Planet size: Giant”, “Non-gas giant”, and “Contains any/gas/non-gas giant” intentionally have
   different predicates/scopes. Add compact help text rather than removing them.
6. The current UI uses “RGB biome”; retain that wording and “ordinary / normal group”. Avoid
   presenting generated hue families as visual-color guarantees.
7. The source has two criteria vocabularies by design: form widget aliases (`population_label`,
   `resource_label_1..3`) are converted by `read_form_criteria`/`build_criteria` to protocol names.
   They should not be added to the protocol allow-list as duplicate criteria.
8. `Any` is not an evaluator comparison. It disables a native field or skips a snapshot predicate;
   this is important for future UI simplification and prevents stale hidden-tab values from leaking
   into presets.
